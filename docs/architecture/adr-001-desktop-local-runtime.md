# ADR-001：桌面端采用同仓库 Monorepo、Electron 安全壳与独立 Local Agent Runtime

- 状态：部分被取代；Monorepo 与独立 Runtime 决策继续有效，Electron 长期产品壳决策由 [macOS 原生 Swift 重构计划](./macos-native-swift-migration-plan.md) 取代
- 日期：2026-08-23
- 适用范围：Roundtable Web、Desktop 及其共享领域、协议、编排、运行时与存储代码
- 关联文档：[Roundtable 桌面版运行时改造路线](./desktop-runtime-migration.md)

> 2026-09-13 决策更新：本 ADR 中 Electron/Renderer/Main 的描述保留为 Phase 1–3 历史基线和迁移期行为约束。正式 macOS 产品的对应角色改为 SwiftUI/AppKit App 与 Swift Host Runtime；正式发行包最终不包含 Electron、Chromium 或 Node host。

## 背景

Roundtable 当前以 Next.js 应用为主要交付形态。其领域模型、Mission 编排、调度器、Agent adapter、持久化和 UI 已形成可复用资产，但现有进程模型主要服务于 Web 请求和开发期本地执行。

桌面产品需要承担不同的系统责任：选择并约束本地工作区，启动和管理 CLI/PTY 及其进程树，持有长生命周期 Mission，处理审批、密钥和系统权限，并在应用退出、崩溃或重启后结算执行状态。这些责任不能由浏览器 Renderer 安全地承担，也不应继续隐含在 Next.js 请求生命周期中。

同时，桌面化不能造成 Web 与 Desktop 两套领域规则、调度器和 UI 长期分叉。现有 Web 产品必须在迁移期间保持可运行，架构调整应允许小步抽取并持续回归。

## 决策驱动因素

- Mission、Turn、Task、Dispatch、Artifact 和 review/fix 规则需要单一事实来源。
- 本地 Agent 执行必须具备明确的权限、生命周期、停止和恢复语义。
- Renderer 必须保持低权限，不能直接接触 Node、Shell、任意文件系统或密钥。
- Electron Main 应保持为应用生命周期与系统集成层，不能演变为新的业务单体。
- Web 与 Desktop 需要独立构建和发布，但共享契约变更应能够原子提交、共同测试。
- 改造必须支持渐进迁移，不能以一次性目录搬迁或重写现有产品为前提。

## 决策

### 1. Web 与 Desktop 保持在同一仓库，并逐步演进为 Monorepo

Roundtable 将在当前仓库内同时维护 Web 应用、Desktop 应用和共享 packages。应用目录只负责各自的组合根、平台接入和发布配置；领域模型、事件协议、编排、运行时、存储抽象和可复用 UI 按稳定边界逐步抽取。

选择同仓库的原因是：

- 领域规则和调度语义可以由同一实现与同一组契约测试约束，避免 Web/Desktop 行为漂移。
- IPC/RPC schema、领域类型及其调用方可在一个变更中同步升级，减少跨仓库版本错配。
- 现有代码可按依赖方向逐步抽取，无需先复制再合并，也无需暂停 Web 开发。
- CI 可以分别验证 Web、Desktop 和共享 packages，同时运行跨边界集成测试。
- UI 和 adapter 的复用发生在显式 package 边界，而不是通过复制文件或让 Desktop 依赖 Web 私有实现。

同仓库不意味着形成一个不可分割的应用。Web 和 Desktop 必须拥有独立入口、构建、测试与发布流程；共享 package 不得反向依赖任一应用。Desktop 不得通过导入 Next.js route、server action 或 Web 进程内部状态来获得本地能力。

### 2. Electron 是安全壳和系统集成层，不是网页 Wrapper

Electron 用于窗口生命周期、原生菜单、文件/目录选择、通知、深链接、更新入口以及本地 Runtime 的启动与监督。它不以“把现有网站装进窗口”作为产品架构或完成标准。

一个纯 Wrapper 仍会把核心执行责任留在 Web 服务或页面生命周期中，无法可靠解决本地工作区授权、CLI/PTY 管理、进程树清理、离线执行、崩溃结算和密钥边界；它也容易把特权能力直接暴露给 Renderer，扩大远程内容或 XSS 的影响范围。

Electron 进程职责固定为：

- **Renderer**：展示状态和收集用户意图；按不可信 UI 对待，不启用 `nodeIntegration`，不直接访问 Shell、文件系统、密钥或 Runtime。
- **Preload**：暴露最小、类型化、可校验的能力接口；不提供通用命令执行、任意路径读写或原始 IPC 通道。
- **Main**：管理窗口、应用生命周期和操作系统集成，监督 Local Agent Runtime，并在 Renderer 与 Runtime 之间实施认证、授权和消息路由。

领域编排、任务队列和 Agent 执行逻辑不得沉入 Main。复用现有圆桌 UI 是允许且鼓励的，但复用的是组件和领域协议，而不是把现有服务器连同其信任假设原样包进 Electron。

### 3. 建立独立的 Local Agent Runtime

桌面端的 Agent 执行由独立 Local Agent Runtime 负责。该 Runtime 是独立于 Renderer、Electron Main 和 Next.js 请求生命周期的受监督本地进程，并通过版本化、可校验的命令/事件协议与宿主通信。

Runtime 负责：

- 持有可持久化的 Mission 执行队列和调度状态；
- 启动、观察、超时、取消并清理 CLI/PTY 子进程及其进程树；
- 统一 Codex、Claude Code、OpenCode 等本地 adapter 的生命周期语义；
- 在已授权工作区内收集真实文件变化、日志和 Artifact；
- 执行环境变量白名单、Secret broker、文件访问和命令执行审批；
- 产生可重放的领域事件，并在宿主重连或应用重启后完成状态对账。

Runtime 的公开契约不得依赖 Electron 或 Next.js API，使其可以独立测试，并为未来的无界面执行、远程控制或替换桌面宿主保留空间。Main 可以启动、停止和健康检查 Runtime，但不能绕过协议直接操纵其内部队列。

“独立进程”是故障和权限边界，不等同于完整安全沙箱。执行不受信任代码仍需额外的操作系统权限控制、沙箱或远程隔离策略。

### 4. 共享领域协议是边界，不以 UI 状态或进程内部对象作为集成方式

Renderer、Main、Runtime 和 Storage 之间以明确 schema 表达命令、审批、状态转换、事件、错误和取消结果。跨边界消息必须可验证、可版本化、可关联到 Mission/Turn/Task，并支持幂等处理。

UI 中的 `running`、`completed` 或 `stopped` 不能只由前端乐观状态决定；它们必须来源于 Runtime 与持久状态的已确认转换。停止操作的完成语义是目标进程树已终止或被明确标记为无法终止，而不是按钮请求已经发出。

## 考虑过的替代方案

### 单独建立 Desktop 仓库

优点是发布权限和构建工具完全隔离。缺点是领域类型、调度器、adapter 和 UI 很快产生复制或跨仓库包版本协调成本，原子修改与端到端回归更困难。当前共享代码比例和渐进迁移需求使这一成本高于收益，因此不采用。

### 将现有 Next.js 应用直接封装进 Electron

这是最快获得窗口的方式，也可短期用于 UI 验证。但它没有建立本地执行、权限、取消、恢复和离线语义，无法证明桌面产品的核心价值，因此不能作为目标架构或 MVP。

### 在 Renderer 中启用 Node，直接调用文件系统和 CLI

实现简单、调用链短，但会把页面内容与宿主权限合并，使 XSS、第三方依赖或错误 IPC 调用获得高影响能力。该方案不满足最小权限原则，明确拒绝。

### 把编排器、存储和 Agent 执行全部放入 Electron Main

该方案减少早期进程间通信，却会让窗口生命周期、系统集成和长任务执行互相阻塞，形成难测试、难恢复、难复用的新单体。它也让 Main 崩溃与 Agent 执行故障相互放大，因此不采用。

### 继续在 Next.js server actions/API route 中运行本地 Agent

这可以最大化复用现状，但请求生命周期不是持久任务监督器，无法可靠拥有 PTY、进程树、租约、应用重启恢复和真正取消。Web 服务可继续发起或观察任务，但不应成为桌面本地进程的所有者。

### 一开始安装常驻系统服务或独立守护进程

系统服务有利于无人值守和跨窗口运行，但会显著增加安装、升级、权限、端口发现和卸载复杂度。MVP 先采用由 Desktop Main 启动并监督的独立 Runtime 进程；当出现明确的后台运行或多客户端需求时再重新评估常驻服务。

### 改用 Tauri 或原生桌面技术栈

这些方案可能带来更小包体或不同的安全模型，但会降低现有 React/TypeScript UI 和 Node CLI 生态的直接复用，并扩大首次桌面化范围。当前选择 Electron；这不是永久排除其他宿主。

## 关键后果

### 正面后果

- Web 与 Desktop 共享领域语义、协议和测试，减少长期分叉。
- 本地进程拥有者清晰，真实停止、超时、进程树清理和崩溃对账可以被端到端验证。
- Renderer 权限面显著缩小，密钥和通用系统能力不会进入 UI 上下文。
- Runtime 可脱离 Electron 与 Next.js 单独测试，并为未来 headless 或远程控制保留复用空间。
- 迁移可围绕可工作的纵向切片推进，Web 无需等待桌面重构完成。

### 成本与风险

- Monorepo 需要新的 workspace、构建缓存、依赖边界和分层 CI 约束。
- 多进程架构引入协议版本、连接恢复、事件排序、背压、日志关联和调试成本。
- Desktop 发布物需要正确打包 Runtime 及其依赖，并处理 macOS、Windows 的进程与权限差异。
- 状态一致性必须通过事务、租约、幂等命令和恢复流程实现，不能依靠内存对象。
- Electron 的安全默认值、CSP、导航策略、更新与供应链仍需持续审计；采用安全壳并不会自动消除风险。

### 组织约束

- 跨应用复用必须通过共享 package 和协议完成，不允许以临时复制形成第二套核心。
- 新增特权能力必须先定义最小 schema、授权范围、审计事件和撤销/取消语义。
- 确定性 fallback 必须被标记为 fallback，不能与真实 Agent 执行成功混为同一产品结果。

## 非目标

本 ADR 不决定或承诺：

- 一次性完成全部目录迁移或确定每个最终 package 的精确文件归属；
- 重写现有 Web 产品，或要求 Desktop 首版覆盖全部 Web 功能；
- 在首个纵向切片中接入所有 Agent、所有 adapter 或所有操作系统；
- 把独立 Runtime 宣称为可安全执行任意不受信任代码的完整沙箱；
- 解决全部现有 workflow 假闭环、远程协作、云端调度或 A2A 产品方向；
- 定义代码签名、公证、自动更新、商店发行和长期运维的具体方案；
- 向 Renderer 提供通用终端、任意 Shell、任意文件系统或直接密钥访问能力。

## MVP 纵向切片

架构方向必须由一条真实、可观察、可停止、可恢复的链路验证：

1. 用户通过系统选择器授权一个本地仓库；
2. 用户创建 Mission，并在执行前明确审批；
3. Main 通过协议把已授权任务交给 Local Agent Runtime；
4. Runtime 启动一个真实 Agent CLI，并流式返回可关联的状态和日志；
5. UI 展示由实际文件变化产生的 Artifact，而不是仅展示 Agent 叙述或确定性模板；
6. 用户停止任务后，Runtime 终止完整进程树并返回已确认的终态；
7. 关闭并重新打开应用后，持久状态能够恢复，未正常结束的执行被重连、重试或明确结算，不留下永久 `running` 的幽灵任务；
8. 同一提交下，现有 Web 应用仍能构建并通过核心回归测试。

把网页加载进 Electron、播放模拟事件或由 `local-dispatch` 生成模板产物，都不算完成这条纵向切片。

## 未来重新评估条件

出现以下任一情况时，应重新评估本 ADR 的相应部分，并以新 ADR 取代而不是静默偏离：

- Desktop 需要在 UI 退出后长期后台运行、开机启动，或同时服务多个本地客户端；此时评估常驻系统服务。
- Web 需要远程控制用户机器上的 Runtime，或 Runtime 需要部署到局域网/云端；此时评估认证、加密传输和远程协议边界。
- Electron 的包体、内存、安全审计或平台限制成为主要产品障碍；此时重新比较 Tauri 或原生宿主，同时保持领域协议不变。
- Monorepo 的权限、发布节奏或构建规模导致团队无法独立交付，且共享 packages 已具备稳定版本契约；此时评估拆分仓库。
- 本地执行需要强隔离不受信任代码，现有 OS 权限和审批模型不足；此时评估容器、虚拟机、系统沙箱或远程执行。
- Runtime 协议无法支持恢复、幂等取消或多版本客户端，或其演进频率使跨进程成本超过隔离收益；此时重新审视进程边界与协议粒度。

在这些条件出现前，同仓库 Monorepo、Electron 安全壳和独立 Local Agent Runtime 是桌面改造的架构基线。
